# M3 Multiplayer: handoff note

Branch `m3-multiplayer`. Built and verified in a GPU-less cloud container (4 cores, 15 GB RAM,
Ubuntu 24.04, Mesa lavapipe) on 2026-10-28. New pinned dependencies: `lightyear =0.30.1` (already
pinned at M0, now used with `default-features = false` and `std, client, server, netcode, udp`),
`serde_json =1.0.154`, `getrandom =0.3.4` and `ureq =3.5.0` (no TLS); `tokio` gained its `time`
feature. Bevy, Avian and every other version are unchanged.

## What runs where

| Process | What it does |
|---|---|
| `racer-server` (one per race) | Headless Bevy app, single-threaded, no renderer or assets: track colliders, Avian + `racer-dynamics` for every car, the race rules (`RacePlugin`, unchanged from single player), AI drivers in slots no player takes (and for players who leave), at 240 Hz. Lobby → countdown → race → results → exit. |
| `racer-game` / bot clients | The same simulation for the local car only (predicted), remote cars as kinematic bodies on extrapolated paths, the race state from the server, the HUD and results of single player. |
| `racer-backend` | Device-key identities, invite-code lobbies, quick match, and a `Fleet` that starts `racer-server` processes (local process spawner). |

### lightyear's part, and ours

lightyear 0.30.1 builds against Bevy 0.19.1 and Avian 0.7 (it has an Avian integration,
`lightyear_avian3d`). It is used for everything below the game: UDP sockets, netcode.io
connections (protocol id, 32-byte key), reliable and unreliable channels with message
(de)serialization and fragmentation, ping/RTT/jitter, the clock sync that keeps each client's tick
ahead of the server's by half the round trip plus a jitter margin (so inputs arrive before the
server simulates their tick), and the link conditioner (latency, jitter, loss) for the tests.

Prediction, rollback, the remote-car model and the race-state replication are ours
(`crates/racer-sim/src/net/`), on lightyear messages. lightyear's prediction/rollback (and its
Avian integration) replays the whole `FixedMain` schedule for every predicted entity and offers
either predicted or delayed-interpolated remote entities. The plan asks for something else:
remote cars *extrapolated* from their last snapshot with their last inputs, and a rollback of the
local car only (PLAN.md section 11's mitigation for the cost of rolling back 8 cars at 240 Hz).
Measured below: replaying the whole 8-car world costs about 2.6 times as much per tick as replaying
the local car against kinematic remote cars, and the bot check runs 8 clients plus the server on
4 cores.

### Ticks and rates

| | Rate |
|---|---|
| Simulation (server and clients) | 240 Hz (`racer_sim::tick_duration`, 4.1667 ms) |
| Snapshots, server → each client | 60 Hz (every 4th tick) |
| Race state (`Standings`), server → clients | each racer at 10 Hz, round robin |
| Inputs, client → server | once per client frame, each message repeating the last 48 ticks (200 ms) |
| Client clock lead over the server | RTT/2 + 4 × jitter + 7 ticks (lightyear sync; 6 ticks over lightyear's default margin) |

### Messages (`racer_sim::net::protocol`)

| Message | Direction | Channel | Content |
|---|---|---|---|
| `Join` | C → S | reliable | name, car id, ABS/TCS/ESC |
| `Inputs` | C → S | unreliable | last tick + up to 48 quantized `NetControls` (throttle, brake, handbrake, clutch as u8, steer as i16, shift/automatic/assist flags) |
| `RequestReset` | C → S | reliable | the reset key / the bot AI asking for a reset |
| `LobbyStatus` | S → C | reliable | players joined, players expected, seconds until the server starts anyway |
| `RaceStart` | S → C | reliable | race config, grid (slot, car, name, driver), the receiver's slot, the tick the race was created on and its first running tick |
| `Snapshot` | S → C | unreliable | server tick; per car: position, rotation, linear and angular velocity, the inputs applied, ghosted; the receiver's `VehicleState` (wheel spin, slips, gear, clutch, ABS/TCS state); newest input tick received |
| `Standings` | S → C | unreliable | one racer's `Racer` (progress, timing, status, position, resets, ghosting), race phase, winner time |
| `RaceOver` | S → C | reliable | every racer's final state |

Controls are quantized on the client *before* it drives with them, so the client predicts with
exactly the values the server applies. A snapshot is about 700 bytes (60 Hz: ~42 KB/s down per
client); inputs ~340 bytes per frame (~20 KB/s up at 60 fps).

### What is predicted, extrapolated, replicated

- **Local car: predicted with rollback.** Each fixed tick the client keeps the quantized inputs
  and the predicted state (rigid body + `VehicleState`) by tick. When a snapshot's state for tick
  `T` differs from the prediction for `T` by more than 1 cm, 0.3°, 5 cm/s, a gear or 0.5 rad/s of
  wheel spin, the car is put back to the server's state and ticks `T+1 ..= now` are replayed
  through `FixedMain` (Avian + `racer-dynamics`) with the kept inputs, the remote cars on their
  recomputed paths. The jump this makes at the current tick is carried by the displayed car and
  decays with a 25 ms time constant (gone in about 4 frames); jumps over 5 m (resets) snap.
- **Remote cars: extrapolated.** Kinematic bodies (they push the local car and are not pushed),
  placed each tick on a path that starts at their last snapshot and runs the point-mass car model
  the AI plans with (drive, braking, grip limit per car) and a kinematic bicycle for the yaw rate,
  under the inputs the server last applied to them (`net::extrapolate`). Every new snapshot
  re-runs the path from its tick; the displayed jump decays with a 40 ms time constant (smoothed
  over ~120 ms). They only collide with cars and skip the vehicle model.
- **Car-to-car contact** is predicted by the local car against the extrapolated remote cars and
  resolved by the server; the correction is blended like any other.
- **Race state is the server's:** countdown (the start tick is sent with the grid, so the client
  holds its car on the brakes for exactly the ticks the server does), laps, positions, sector and
  lap times, resets and ghosting, finish and DNF come in `Standings` and `RaceOver` and replace the
  client's `Racer` components. The race rules do not run on clients (`RemoteRace`).
- **The server trusts inputs only.** A late or lost input repeats the last one (shift requests
  excepted); a client's prediction then differs and is corrected.

## Backend v1 (`racer-backend`)

`cargo run -p racer-backend` (listens on `RACER_BACKEND_ADDR`, default `127.0.0.1:8080`). All
state is in memory; `RACER_BACKEND_STATE=<file>` keeps the players in a JSON file across restarts.

| Endpoint | What |
|---|---|
| `GET /health` | `"ok"` (unchanged) |
| `GET /v1/me`, `POST /v1/me {name}` | the caller's player (id, name); renaming |
| `POST /v1/lobbies {settings}` | new invite lobby, caller as host; answers the lobby with its 6-character code (no 0/O/1/I) |
| `GET /v1/lobbies/{code}` | the lobby (members only; the client polls it twice a second) |
| `POST /v1/lobbies/{code}/join {car}`, `/leave` | join by code (any case; leaves other lobbies); leave (the next member becomes host) |
| `POST /v1/lobbies/{code}/ready {ready, car}` | ready state and car |
| `POST /v1/lobbies/{code}/settings {track, mode, laps, collisions, ai_fill}` | host only, while open; un-readies the others |
| `POST /v1/lobbies/{code}/start` | host only, everyone ready: allocates a server, the lobby turns `racing` with the server's address and the race's key |
| `POST /v1/quickmatch {mode, class, car}` | joins the open public lobby for that mode and class (`open`, `hot-hatch`, `sport-sedan`, `sports-gt`) or opens one; it starts by itself after 15 s or with 8 players, AI in the empty slots |

**Identity.** Every request carries `x-device-key: <64 hex digits>`, a random secret the game
makes on first use and keeps in its config directory (`device-key`). The backend registers an
unknown key as a new player. No accounts, no passwords.

**Servers.** `Fleet` (`fleet.rs`) is `fn allocate(&self, &RaceRequest) -> Result<Allocation>`.
`LocalFleet` starts `racer-server --bind <RACER_FLEET_BIND>:0 --players N --laps ... --mode ...
--collisions ... [--no-ai-fill]` with a fresh random netcode key in `RACER_SERVER_KEY`, reads the
`racer-server listening on ADDR` line from its stdout, and reaps the process when it exits after
its race. The lobby then shows its members the address (`RACER_FLEET_PUBLIC` replaces a wildcard
or private bind address) and the key; clients connect with a token they make from that key and
their player id. The server waits for the lobby's players (60 s at most, then races with who is
there).

## Client

Main menu: Race (single player, unchanged), **Quick match**, **Create lobby**, **Join lobby**
(type the code), **Direct connect** (type `host:port`, development), Quit. `racer-game connect
HOST:PORT [--car N] [--autopilot]` goes straight to a server.

The lobby screen lists the members (host, ready, car), the settings, and the status line; the host
changes mode, laps, collisions and AI fill and starts the race, the others pick a car and toggle
ready; Leave returns to the menu. Once the server sends the grid the race scene comes up with the
single-player HUD, minimap and results, fed by the server's race state, plus the round-trip time
at the bottom (red, with "high latency", above 250 ms). Esc opens a menu that does not pause the
race (Resume, Leave); the results offer only Main menu. A server that does not answer, or goes
away, shows as an error on the lobby screen; backend errors come back to the main menu's subtitle.

Screenshots (`tools/capture.sh lobby`, goldens in `crates/racer-capture/goldens/lobby/`): the
code entry and a host's lobby. `tools/capture.sh online` (with a server on `127.0.0.1:7777`) takes
the lobby and the online race HUD; it is a manual check, since a software-rendered client runs
at about 1 fps and cannot keep a real-time race clock.

Single player is unchanged: the greybox, driving, menu setup and race captures still match their
goldens (race: bit-identical), and `racer-capture ai-races --races 12 --laps 3` gives the same 68
contacts and 0 resets as before. The main menu golden was updated for its new entries.

## Problems found while building, and fixes

1. **The 8-bot race spiralled.** The first 8-bot runs at 150 ms had 37 % of snapshots needing a
   correction, 70 % of the players' ticks driven with a repeated input, and the bots at 20 fps
   spending 40 % of their time replaying. Late inputs (the server repeats the last one) made the
   predictions wrong, the replays took the CPU the next inputs needed, and those came later still.
   Four fixes, measured together on 8 bots × 3 laps: 0.2 % of snapshots corrected, 0.7 % repeated
   inputs, every bot at 60 fps:
   - the client's clock lead got 6 more ticks of margin (lightyear's default, 4 × jitter + 1
     tick, gave 4 ticks, and inputs came ~20 ticks late whenever a frame did);
   - remote (kinematic) cars no longer run the vehicle model: each did 4 wheel shape casts per
     tick for nothing, which made seven of them cost as much as the local car (`net-cost`: one
     client tick 495 → 274 µs);
   - they only collide with cars (no contact generation against the track);
   - the server runs single-threaded like the M2 simulations (Bevy's multi-threaded executor
     cost more in synchronisation than it gained), and a prediction is only corrected when it is
     1 cm, 0.3° or 5 cm/s off (1 mm before: float-level differences triggered replays).
2. **lightyear adds its systems in `Plugin::finish`.** An app driven with `update()` by hand
   (the tests) must be finished first, or nothing is ever sent.
3. **Standings of a second race were dropped**: the newest-tick filter outlived the race. It now
   lives with the race's prediction state.
4. **A connection that never came up** left the client "connecting" forever; it now fails after
   2 s of netcode refusing, with a message on the lobby screen.
5. **Inputs from a client were not bounded**: a malformed `Inputs` could make the server keep any
   number of future ticks. Only the next 2 s are kept.

## Known gaps

- **Connect tokens.** The backend hands the lobby's members the race's netcode key and each
  client makes its own token; a member could therefore connect under another member's id.
  Tokens made by the backend (lightyear_netcode's `ConnectToken`) are the next step. The backend
  speaks plain HTTP (no TLS) and its state file keeps the device keys as they are.
- **Contact on the client is against an immovable car.** Remote cars are kinematic, so in a
  predicted contact the local car bounces off a car that does not give way; the server resolves
  it with both cars moving and the local car is corrected (the "near contacts" corrections in the
  tables). Predicting the other car's response (making the contacted remote car dynamic for the
  replay, PLAN.md's "contacted bodies") is not done.
- **Remote cars' wheels** don't turn or steer (their vehicle model is not run on clients and the
  snapshot carries no wheel state), and their race data (position, laps) on the HUD and minimap
  is updated at 10 Hz.
- **No rejoining** a race after a disconnect: the AI takes the car over, and a `Join` after the
  start is ignored. No spectators, no chat, no kicking (vote-kick is M6).
- **Quick-match classes** group players, but the server does not check that a car is of the
  class.
- **Online play was not driven by a person here.** The game's online screens are covered by
  goldens and the online race by a software-rendered screenshot (HUD, ping, cars), but that client
  runs at about 1 fps, so its race is not representative; the bots exercise the same client code
  headless. A GPU machine should play a lobby race once.
- **The net check is one machine.** Eight clients and the server share 4 cores; the server's
  longest tick (tens of ms) is OS scheduling, and about 0.2 % of the players' ticks are driven with
  a repeated input (most around the start, before the first inputs arrive).
- Windows and macOS only type-check (cross-target clippy); CI still cannot start jobs on this
  account (see M0).
