### racer-capture

`racer-capture scene <name> <out-dir>` opens a window (1280×720 by default), adds the scene and a
`CapturePlugin`, and for each scripted pose (greybox: `front-three-quarter`, `side`, `rear-high`):

1. moves the `SceneCamera` to the pose;
2. waits until the render world's `PipelineCache` has at least one pipeline and **zero queued,
   compiling or failed pipelines for 10 consecutive frames** (a render-world system in
   `RenderSystems::Cleanup` publishes the counts to the main world through an `Arc` of atomics);
3. takes a `Screenshot::primary_window()` and runs `check::check` on it (rejects >90 % one colour,
   luma stddev < 4, or mean luma outside 8..247); a rejected frame is retried;
4. writes `<pose>.png`.

The whole run has a deadline (`--timeout`, default 600 s); on timeout, a write error or an
unconvertible image it logs the pipeline counts and exits 1. Bad usage exits 2.
`racer-capture check <png>...` and `racer-capture diff <actual> <golden>` (files or directories;
tolerances `--pixel`, `--max-fraction`, `--max-mean`) are the stand-alone image tools. Goldens live
in `crates/racer-capture/goldens/greybox/`.

The greybox scene: 2 km asphalt-grey ground plane with lane stripes, a 4.3 × 1.45 × 1.8 m box with
`car_paint` (clearcoat 1.0, clearcoat roughness 0.05) on four wheels, a shadow-casting sun
(`RAW_SUNLIGHT`, cascaded shadows) and Bevy's physical `Atmosphere` with
`AtmosphereEnvironmentMapLight` for sky ambient, `Exposure { ev100: 13 }`, ACES tonemapping. The
atmosphere is cheap enough on lavapipe (whole 3-pose capture ≈ 25 s after build).

### CI on three OSes

Every push to this branch created the CI run with all four jobs, and every job failed within
3 seconds **without being assigned a runner** (`runner_id 0`, no steps, billable time 0 ms, the
job-log endpoint returns 404 and the run log archive is empty), identically on Linux, Windows and
macOS (runs 40459748322 and 40461501749). The repository is private, so the most likely cause is
an account-level Actions limit (billing / spending limit / exhausted included minutes). The exact
reason is shown as an annotation on the run page in the GitHub UI, which the agent's API tools
cannot read. This is outside what the code can fix; the repository owner needs to check
*Settings → Billing and plans → Actions* (or make the repository public) and re-run the workflow.

Substitute verification done in the container instead:

```
$ rustup target add x86_64-pc-windows-msvc aarch64-apple-darwin
$ CARGO_FEATURE_PURE=1 cargo clippy --workspace --all-targets --locked \
    --target x86_64-pc-windows-msvc -- -D warnings      # Finished, no warnings
$ CARGO_FEATURE_PURE=1 cargo clippy --workspace --all-targets --locked \
    --target aarch64-apple-darwin -- -D warnings        # Finished, no warnings
```

(`CARGO_FEATURE_PURE=1` makes `blake3`'s build script skip its C/asm path, which needs a target C
compiler that a Linux host lacks; real Windows/macOS runners don't need it.) This proves the whole
workspace type-checks and is lint-clean for both targets, but not that it links or that tests pass
there. **The first green CI run is still owed** once Actions can start jobs.

lightyear 0.31, bevy_egui 0.43, bevy_kira_audio 0.27, require Bevy 0.20). They were verified together

without errors. When a crate starts using one, add `foo.workspace = true` to its `[dependencies]`.
No ecosystem crate had to be left out. `sqlx`, `gilrs`/`sdl3` are not pinned yet: nothing uses them
and they don't depend on Bevy.

Build profile: `[profile.dev] opt-level = 1, debug = "line-tables-only"`, all dependencies at
opt-level 3 without debug info. One target dir (`target/`), ≈ 6 GB after a full build + clippy +
cross-target checks.

## Known gaps and deferred work

The CI matrix has not run (see above). Golden diffs in CI assume the runner's lavapipe matches
the container's (both Ubuntu 24.04 Mesa); if the first CI capture differs slightly, inspect the
uploaded artifact and either widen the tolerance or regenerate goldens from CI output. The plan's
Windows (WARP) and macOS CI captures are not set up; only the Linux capture job exists.
`racer-capture` knows one scene and fixed poses; per-track flythroughs, time/weather sweeps and
telemetry come with the tracks. `racer-trackc` and `racer-dynamics` are skeletons by design.
`tools/setup.sh` supports apt-based Linux only.
